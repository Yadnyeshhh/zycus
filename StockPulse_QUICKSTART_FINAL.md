# StockPulse — Quick Start

## 1. What This Project Does

StockPulse automates:

**Detect → Recommend → Approve/Reject → Act**

The main demo flow is:

**Inventory/order change → automatic trigger → AI/rule recommendation → PENDING suggestion → merchandiser decision → live action**

The HTML problem statement is the source of truth for scope.

---

# 2. Prerequisites

Install:

- Java/JDK version required by the Spring Boot project
- Maven (or use the Maven Wrapper)
- Node.js and npm
- Git

No Redis, Kafka, Docker, Kubernetes, or other external infrastructure is required by the core implementation.

H2 is used for the hackathon database setup.

# 9. Main Demo Scenario — Low Inventory

Use a product whose stock can be reduced below its reorder threshold.

### Flow

1. Start backend.
2. Start frontend.
3. Open the merchandising console.
4. Locate the product.
5. Perform the order/inventory action required by the demo.
6. Confirm stock decreases.
7. Confirm the system detects low inventory.
8. Confirm an `INVENTORY_LOW` recommendation is generated automatically.
9. Confirm the suggestion appears as `PENDING`.
10. Open the suggestion.
11. Show:
   - trigger reason
   - recommended price
   - reorder quantity where applicable
   - confidence
   - AI reasoning
12. Accept the suggestion.
13. Confirm the live product state changes according to the accepted action.

Important:

The recommendation should be generated by the automatic trigger flow. Do not manually generate it from a dashboard button for this scenario.

---

# 10. Main Demo Scenario — Demand Spike

Use a product/category where demand velocity can be made greater than:

```text
2 × category average velocity
```

### Flow

1. Perform the required demand/order action.
2. Confirm demand velocity increases.
3. Confirm the system detects `DEMAND_SPIKE`.
4. Confirm a recommendation is generated.
5. Confirm it is `PENDING`.
6. Open the recommendation.
7. Show that the trigger badge says `DEMAND_SPIKE`.
8. Show reasoning and confidence.
9. Accept or reject it.
10. Confirm the resulting product state matches the decision.

# 11. Rejection Demo

This demonstrates the human-in-the-loop requirement.

1. Generate a pending suggestion.
2. Open it.
3. Click Reject.
4. Confirm the suggestion status becomes `REJECTED`.
5. Confirm the live product price/stock is NOT changed by the rejected suggestion.

This is important because StockPulse must recommend, but a human decides whether the recommendation becomes live.

---

# 12. Idempotency Demo

1. Trigger the same relevant condition.
2. Allow the recommendation to become `PENDING`.
3. Trigger the same condition again while the existing suggestion is still pending.
4. Confirm that a duplicate pending suggestion is not created.

This proves the required idempotency behavior.

---

# 13. AI Fallback Demo

If practical during the hackathon, simulate an AI failure such as:

- timeout
- provider/API failure
- malformed response

Expected behavior:

```text
AI failure
   ↓
Rule-based fallback
   ↓
Valid suggestion
   ↓
PENDING
```

The application should remain usable.

# 14. Manual Recommendation API Demo

The HTML also requires on-demand recommendation endpoints.

Use:

```text
POST /products/{id}/suggest-pricing
POST /products/{id}/suggest-reorder
```

These should create the corresponding suggestion without requiring a dashboard button.

Use them for API testing; the primary business demonstration should still show the automatic agentic loop.

# 15. Runtime Strategy Switching

The system must support switching the active commerce strategy at runtime without restarting the application.

Verify this before the final demo.

Test:

```text
Rule-based strategy
        ↓
switch strategy
        ↓
AI-assisted strategy
```

without restarting Spring Boot.

The exact runtime-switch mechanism should match the implementation.
